# АСКК — Автоматизированная система контроля качества продукции

Информационная система отдела технического контроля (ОТК) для **ОАО «Амкодор-Пинск»**:
учёт производственных партий, оформление актов проверки, регистрация дефектов,
контроль их устранения и аналитическая отчётность.

## Запуск онлайн (GitHub Codespaces)

[![Open in GitHub Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/MISHKA3034/quality-control?quickstart=1)

Кнопка создаёт облачное окружение с .NET 10, Node.js и SQL Server
(настройки — в [.devcontainer](.devcontainer)). Первый запуск занимает 3–5 минут:
скачивается образ SQL Server, применяются миграции и создаются демо-данные.
После этого клиент открывается в браузере сам (вкладка **Ports → 5173**).

Учётные записи в Codespaces: `admin` / `Admin123!`; демо-пользователи
(`inspector`, `master.cmk`, `production` и др.) — `Demo1234!`.
Логи: `/tmp/askk-api.log`, `/tmp/askk-client.log`.

> Пароли выше — только для одноразового демо-окружения. Codespace засыпает
> после ~30 минут простоя; бесплатная квота GitHub — около 60 часов в месяц.

## Архитектура

```
src/
├── QualityControl.Domain          Сущности, перечисления, бизнес-правила. Без зависимостей.
├── QualityControl.Application     Сценарии, DTO, интерфейсы, валидаторы, маппинг.
├── QualityControl.Infrastructure  EF Core, репозитории, JWT, хранение файлов, экспорт.
└── QualityControl.API             Контроллеры, аутентификация, middleware, Swagger.
client/                            SPA на React + TypeScript.
```

Зависимости направлены строго внутрь и проверяются компилятором:
в `QualityControl.Domain.csproj` нет ни одной ссылки на пакет.

**Правила живут в доменных сущностях, а не в сервисах.** Переходы статусов партии и
корректирующего действия описаны таблицами внутри
[ProductionBatch](src/QualityControl.Domain/Entities/ProductionBatch.cs) и
[CorrectiveAction](src/QualityControl.Domain/Entities/CorrectiveAction.cs);
недопустимый переход невозможно выполнить в обход. У `CorrectiveAction` сеттер статуса
приватный — единственный вход `ChangeStatus()`, который сам пишет историю.

**Компромисс.** Слой Application ссылается на EF Core — только ради асинхронных операторов
`IQueryable` и `ProjectTo`. Это позволяет выполнять фильтрацию, сортировку и пагинацию
в SQL. Альтернатива (материализация в репозитории) тянула бы таблицы целиком на каждый
список. `DbContext` в Application не используется: вся персистентность в Infrastructure.

## Быстрый старт

### 1. Секреты

Ключ подписи JWT намеренно **отсутствует** в `appsettings.json`: ключ в репозитории —
это опубликованный ключ, по которому можно выпустить токен администратора. Приложение
не стартует без него и сообщает об этом явно.

```powershell
cd src/QualityControl.API

# Ключ подписи JWT (не короче 32 символов)
dotnet user-secrets set "Jwt:Key" "<32+ случайных символов>"

# Пароль первого администратора. Без него учётная запись не создаётся
# (в журнал пишется предупреждение) — чтобы в системе не появился
# аккаунт со всеми правами и заранее известным паролем.
dotnet user-secrets set "Seed:AdministratorPassword" "<пароль>"

# Пароль демонстрационных учётных записей (только для Development)
dotnet user-secrets set "Seed:DemoUserPassword" "<пароль>"
```

В production те же значения задаются переменными окружения:
`Jwt__Key`, `Seed__AdministratorPassword`.

### 2. База данных

Миграции применяются автоматически при старте (`Database:MigrateOnStartup`).
Вручную:

```powershell
dotnet ef database update --project src/QualityControl.Infrastructure --startup-project src/QualityControl.API
```

### 3. Запуск

```powershell
# API → http://localhost:5090, Swagger UI на /swagger
dotnet run --project src/QualityControl.API --launch-profile http

# Клиент → http://localhost:5173
cd client
npm install
npm run dev
```

> Порт **5090** выбран потому, что на машине разработки уже занят 5080
> (`Amkodor.ToolWarehouse.Api`). Vite проксирует `/api` на 5090 — при смене порта
> нужно поправить и [launchSettings.json](src/QualityControl.API/Properties/launchSettings.json),
> и [vite.config.ts](client/vite.config.ts).

### 4. Демонстрационные данные

При `Seed:DemoData = true` (включено в Development) создаются 5 подразделений,
10 сотрудников, 8 изделий и **год производственной истории**: ~100 партий, ~90 актов
проверки, дефекты и корректирующие действия в разных стадиях. Генератор использует
фиксированный seed — набор одинаков на всех машинах.

Демонстрационные учётные записи (пароль — `Seed:DemoUserPassword`):

| Логин | Роль |
|---|---|
| `admin` | Администратор (пароль — `Seed:AdministratorPassword`) |
| `inspector`, `inspector2` | Контролёр ОТК |
| `master.cmk`, `master.mc` | Начальник участка |
| `production` | Руководитель производства |

## Модель данных

15 таблиц из ТЗ плюс три, без которых требования ТЗ не реализуются:

| Таблица | Зачем добавлена |
|---|---|
| `RefreshTokens` | п.1 «Refresh Token» — хранятся хешированными, с ротацией и цепочкой отзыва |
| `PasswordResetTokens` | п.1 «Восстановление пароля» — одноразовые, короткоживущие |
| `CorrectiveActionHistory` | п.6 «Хранить историю изменений» |

`InspectionResults` смоделирована как **строки акта по контролируемым параметрам**
(требование → факт → вердикт). Общий вердикт хранится в `QualityInspections`; иначе
отдельная таблица дублировала бы одно enum-поле.

**Мягкое удаление** для всех документов качества: акт проверки — это доказательство,
физическое удаление сделало бы историю нереконструируемой. Скрытие удалённых записей
обеспечивают глобальные фильтры EF Core. Журнал действий (`AuditLogs`) фильтра не имеет
и остаётся читаемым полностью.

## Решения по безопасности

- **Пароли** — BCrypt, work factor 12. При входе несуществующего пользователя хеш
  всё равно вычисляется: иначе «нет такого пользователя» отвечал бы заметно быстрее,
  чем «неверный пароль», и вход превратился бы в оракул существования учётных записей.
- **Блокировка** после 5 неудачных попыток на 15 минут.
- **Refresh-токены** хранятся хешированными (SHA-256), ротируются при каждом
  использовании. Повторное использование отозванного токена трактуется как утечка —
  отзывается вся цепочка.
- **Восстановление пароля** всегда отвечает одинаково, независимо от того,
  зарегистрирован ли адрес.
- **Загрузка файлов** — allow-list по типу **и** расширению; имя на диске генерируется
  (GUID), клиентское не используется; файлы отдаются только через API с проверкой прав.
- **CORS** — только явно перечисленные origin, без `AllowAnyOrigin`.
- Тексты исключений отдаются клиенту только вне production.

## Проверено вручную

Backend проверен сквозным прогоном на реальной БД, а не только сборкой:

- вход, выдача JWT, обновление и отзыв токенов;
- оформление акта проверки — акт, строки параметров, дефекты и новый статус партии
  сохраняются одной транзакцией; партия автоматически проходит
  `AwaitingInspection → UnderInspection → ReworkRequired`;
- отказ домена на недопустимом переходе (`409`), валидация (`400` с ошибками по полям),
  разграничение прав (`403`), анонимный доступ (`401`);
- полный маршрут КД: `Новый → Назначен → В работе → Исправлен → Проверен → Закрыт`,
  с записью истории; дефект автоматически перешёл в «закрыт»;
- экспорт всех отчётов в Excel и PDF (кириллица в PDF проверена по встроенным
  подмножествам шрифта и ToUnicode CMap);
- загрузка/скачивание фотографии дефекта, отклонение `.exe`.

**Клиент написан, но не собран и не запущен** — на машине не установлен Node.js.
После `npm install` возможны правки (типы, версии пакетов MUI).

## Найдено и исправлено при проверке

| Проблема | Суть |
|---|---|
| `ValidationProblemDetails.Errors` терялись | `System.Text.Json` сериализует по объявленному типу — ошибки по полям не доходили до клиента |
| Дублирование allow-list загрузок | Биндер конфигурации **дополняет** массив со значением по умолчанию, а не заменяет его — формат нельзя было убрать через appsettings |
| `RefreshToken` → `User` с фильтром | Токен возвращался с `null`-навигацией у soft-deleted пользователя; путь обновления разыменовал бы null |
| `AutoMapper 14.0.0` | Известная уязвимость GHSA-rvv3-g6hj-g44x → 16.2.0 |
| `Microsoft.OpenApi 2.0.0` | Уязвимость GHSA-v5pm-xwqc-g5wc — пакет убран, используется Swashbuckle |

## Лицензии сторонних компонентов

Требует решения предприятия перед промышленной эксплуатацией:

- **AutoMapper 16.x** — с версии 15 платный для организаций с выручкой более $5 млн.
  Версия 14 бесплатна, но содержит уязвимость. Варианты: коммерческая лицензия,
  откат на 13.0.1 или отказ от AutoMapper в пользу ручного маппинга.
- **QuestPDF 2025.7** — Community-лицензия бесплатна при выручке до $1 млн,
  иначе требуется Professional. Объявляется в
  [Program.cs](src/QualityControl.API/Program.cs).
- **ClosedXML**, **BCrypt.Net-Next**, **Serilog**, **FluentValidation** — MIT/Apache 2.0,
  ограничений нет.

## Эксплуатационные замечания

- **Шрифт PDF.** По умолчанию `Segoe UI` (есть в Windows). На Linux-контейнере нужно
  установить кириллический шрифт и задать `PdfExport:FontFamily` (например,
  `DejaVu Sans`) — иначе отчёты отрендерятся пустыми прямоугольниками.
- **Миграции при старте** годятся для одного сервера. При нескольких экземплярах за
  балансировщиком выключите `Database:MigrateOnStartup` и применяйте миграции шагом
  деплоя.
- **Хранение файлов** — локальный диск (`App_Data/uploads`, вне `wwwroot`). За
  балансировщиком нужен общий том либо реализация `IFileStorageService` поверх
  объектного хранилища.
- **Почта** отключена (`Email:Enabled = false`) — письма пишутся в лог, чтобы ссылка
  восстановления пароля была доступна при разработке.
- **IP в журнале** — адрес сокета. За обратным прокси настройте `ForwardedHeaders`,
  иначе в журнал попадёт адрес прокси.
